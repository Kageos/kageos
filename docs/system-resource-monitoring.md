# 系统资源监控

`system` 超管可以在“系统设置 -> 运行状态”查看 kageos 所在服务器的运行负载和存储容量。

## 展示内容

- CPU 核心数、CPU 使用率，以及操作系统支持时的最近 1、5、15 分钟平均负载；
- 内存、Swap、网络收发速率及累计流量、磁盘读写速率；
- kageos 持久化存储所在文件系统的总量、已用量、可用量和使用率；
- 自动识别宿主机存储和 Docker / Podman 虚拟机存储，并按存储池展示容量；
- MySQL、MinIO 对象数据、工作空间、运行数据、日志、HTTPS 证书、容器镜像与存储层、容器构建缓存及其他命名数据卷的占用，以及同一存储池中仍无法归类的其他数据；
- 用户、工作空间、服务目录、函数、应用数据库和定时任务的每日规模快照；
- 基于现有操作日志与函数累计次数的调用量概览，包括每日操作趋势、常用服务目录和常用函数；
- 完整的平台数据库与服务目录数据库清单，包含数据和索引逻辑大小、所属平台服务或工作空间、完整服务目录、用途与登记状态；
- app-storage 已登记文件资产清单，可按工作空间和服务目录筛选，查看上传人、上传时间、预览/下载次数，并执行可审计预览、下载或保留墓碑的删除；
- 最近 7 天或 30 天的数据库逻辑容量、数据库数量及相对上一日的增量，支持按分类、单库筛选和折线图 / 柱状图 / 明细表切换；
- 24 小时、7 天、30 天的 CPU、磁盘、内存和网络走势；
- 到磁盘使用率 85% 扩容线的预计天数。

## 分层采集与保留

采集分成互不阻塞的三类任务：

- 实时运行指标每 30 秒读取一次，仅访问操作系统计数器；每 10 分钟把平均 CPU、最高 CPU、网络和磁盘 IO 平均速率及最后状态写入 `system_resource_samples`；
- 平台规模每天按服务器本地时区 02:00 由 HR、工作空间、应用运行时和定时任务服务分别执行一次只读聚合，再通过内部 NATS 汇总，写入 `system_platform_snapshots`；
- 容量盘点每天按服务器本地时区 02:30 执行；服务启动时只在上一调度周期缺少快照时补采，结果写入 `system_capacity_snapshots`。目录递归、Docker / Podman 统计和数据库逻辑大小只在该任务中执行。

服务启动时会先读取最近的日快照；当前调度周期已经成功采集过时不会因重启重复执行全盘扫描。当天补采或重试使用替换写入，同一天最多保留一条平台快照和一条容量快照。

历史数据按价值设置独立的滚动窗口：

- 30 秒实时计数只在内存中参与计算，不直接写库；10 分钟运行聚合保留 30 天，最多约 4,320 条；
- 每日平台规模快照保留 90 天；
- 每日容量与完整数据库清单快照保留 365 天，用于计算容量和数量的日增量。

每日容量任务使用硬删除清理每张表各自保留线之前的数据，避免软删除数据继续占用表空间。所有历史表都有固定上限，不会无限累计。页面展示每类任务的上次成功时间、耗时、状态、下次采集时间和对应保留策略。

到达每日调度点时若工作空间、应用运行时或定时任务服务尚未就绪，平台规模会在一分钟后补采一次；应用数据库容量来源会在 5 分钟后补采一次。同一天的补采会替换不完整快照，不会增加历史行数。来源不可用会显示为“部分成功”，不会用零值冒充真实数据。

调用量统计不新增请求级明细。成功的 Table、Form 和 Chart 调用继续使用 `service_tree.run_count` 累计；Form 提交、Table 增删改和定时执行等审计行为继续使用现有 `operate_logs`。平台每日 02:00 把全部函数的紧凑累计计数放入现有平台快照，通过前后快照差值得到 7 天或 30 天函数与目录排行。页面打开“调用量概览”时才执行一次当前汇总读取，不参与 30 秒实时轮询；操作日志只作为操作量和失败量口径，不冒充完整函数调用量。

运行状态页面按“总览、调用量概览、资源趋势、存储空间、数据库资产、采集诊断”拆分；文件资产提升为与运行状态并列的系统设置一级入口。总览进入时加载资源趋势，每 30 秒仍只请求实时指标和平台规模；调用量、趋势、每日存储盘点、数据库清单和采集详情仅在进入对应页签时加载。文件资产也只在进入其一级入口时加载，使用服务端筛选与分页，不再随实时轮询整表传输。

资源接口按刷新频率拆分为 `/resources/summary`、`/resources/usage`、`/resources/trends`、`/resources/storage`、`/resources/databases` 和 `/resources/diagnostics`。原 `/resources` 接口暂时保留作为兼容入口，新页面不再调用它。

文件资产接口由 app-storage 提供，只查询 `file_uploads` / `file_downloads` 元数据，不在页面请求中扫描 MinIO Bucket。它覆盖经 app-storage 上传的业务文件；绕过平台直接写入对象存储的对象缺少可信服务目录、上传人和业务含义，不能冒充业务文件，应由每日低频对象对账任务单独识别。图片显示缩略图，图片、视频和 PDF 可在页面内预览；预览与下载使用不同的审计动作，文件详情中可查看操作人、IP 和时间。MinIO 控制台是基础设施高级入口，生产环境默认不暴露，只有显式配置 `MINIO_CONSOLE_URL` 时才向 system 超管显示跳转按钮。

任一可获取容量的存储池使用率达到 80% 时提示准备扩容，达到 90% 时提示立即扩容；告警会标明具体存储池。主存储积累至少 24 小时历史后，即使当前使用率较低，按近期增长速度预计 30 天内达到 85% 时也会提前预警。

## 环境与存储自动发现

采集器不要求管理员为不同部署方式分别配置。启动后会自动识别：

- 源码开发环境：统计仓库中的 `namespace`、`data` 和 `logs`，并探测开发配置指定的 Docker 或 Podman；
- AIO：优先使用 `KAGEOS_AIO_DATA_DIR`，否则发现 `/var/lib/kageos`；
- 容器化生产：识别容器标记和 `/app` 工作目录；
- 宿主机生产：读取 `.kageos/prod/kage.yaml` 中的 `storage.root`；
- 其他布局：回退到 kageos 根目录或当前系统文件系统根目录。

CPU、内存、Swap、网络、磁盘容量、磁盘 IO 和运行时间使用跨平台系统接口采集，支持 Linux、macOS 和 Windows。Windows 不提供 Unix Load Average 时，页面自动使用 CPU 使用率，不把“不适用”误报成故障。Windows 数据目录使用盘符和原生路径；Docker Desktop / Podman Machine 仍按独立存储池处理。

在 macOS / Windows 的 Docker Desktop 或 Podman Machine 场景中，容器数据位于独立虚拟磁盘。采集器会把宿主机与容器引擎显示为两个存储池，避免把 MySQL、MinIO 占用误算到宿主机磁盘。若容器引擎只提供分类占用、不提供虚拟磁盘总容量，页面会显示已知占用并明确标记“总容量未知”。

开发环境会识别 Docker、Podman 和旧版部署使用过的 MySQL / MinIO 数据卷名称；同时根据卷的当前挂载数优先选择正在使用的卷。其他项目或历史遗留的命名卷不会冒充 kageos 的 MySQL / MinIO 数据，而是统一计入“其他容器数据卷”。构建缓存、镜像与可写容器层也分别统计，最终剩余项才归入“容器引擎其他数据”，避免遗漏或重复计算。

容量采集口径带有版本号。升级后若最近的日快照来自旧口径，服务启动时只补采一次并替换当天快照，使新增的 MinIO、构建缓存等分类立即可见；之后仍按每天一次执行，不会因服务重启反复扫描。

`KAGEOS_MONITOR_STORAGE_ROOT` 仅作为非标准部署布局的显式覆盖，不是正常部署的必填项。该目录必须与真实持久化数据位于同一文件系统，才能正确反映扩容所关心的磁盘容量。

目录占用统计只读取当前 `hr-server` 进程可见的本地目录。使用外部 MySQL、外部对象存储，或没有把对应目录挂载给主容器时，页面会显示“未挂载或使用外部服务”，不会把远端容量误算成本机容量。

数据库逻辑容量来自 `information_schema.schemata` 与 `information_schema.tables` 的汇总。页面盘点 HR 当前连接的 MySQL 实例中账号可见的非系统 schema，并合并 app-runtime 已配置实例与数据库前缀下的物理库；平台服务库、服务目录库和未归属库分组展示，不代表自动连接了未配置的其他实例。共享实例中的工作空间库按 MySQL server UUID 和库名与 runtime 清单对账，避免重复计量；已登记的服务目录库会关联 `app_databases` 补齐工作空间、完整服务目录和状态，只有物理库但没有登记记录时标记为“未登记”，只有登记记录但物理库不存在时标记为“物理库缺失”。数据库账号没有统计权限时显示“不可用”，不会把未知容量当作零。

## 权限

资源接口和“运行状态”页面只允许平台内置的 `system` 超管访问。普通管理员、组织管理员和普通用户不会获得服务器容量、目录结构或运行负载信息。


## 数据库历史与完整性

`GET /hr/api/v1/system/settings/resources/databases` 支持 `days=7|30`、`database=<source_id>/<name>`（旧快照无 source_id 时为库名） 和 `scope=all|platform|workspace|unmanaged`。`keyword` 与分页只筛选清单，不改变图表口径；`include_history=false` 可跳过重复的历史载荷。`history_databases` 包含当前分类在所选期间出现过的库，历史库不会因为当前清单分页而消失。

日界线按服务器时区定义，存储时间统一为 UTC，响应 `date` 固定为采集侧自然日。无采样或采集不完整时保留缺口；只有相邻自然日且盘点口径版本相同才计算日增量。缺失物理库的容量不可当作 0。同一天的失败补采不会覆盖已经完整的快照。盘点版本升级后会补采新范围，旧历史不能凭当前库大小回填。

## 日志归档恢复

系统管理员可通过归档列表的“立即重试”或 `POST /workspace/api/v1/system/log_archives/:id/retry` 续跑指定批次。该操作复用归档功能本身的源日志保留策略：导出数量校验、上传、完整对象 SHA-256 与字节数校验、登记成功并持久化上传检查点后，才清理选中的源日志 ID。

- 上传或导出失败保留源日志；已验证的批次从源日志清理阶段恢复，包括旧版标为失败但已有验证证据的批次。
- 清理中断或最终完成状态写入失败可重复重试；已完成批次再次请求不会重复执行。
- 手动和定时执行通过 MySQL 连接锁互斥；进程退出后数据库释放锁。
- 失败批次记录尝试次数和自动重试最早时间，以 15 分钟起步指数退避，最长 16 小时。真正的自动尝试由后续归档调度触发；“立即重试”可绕过退避等待。
- 单个失败批次不阻塞其他批次，其已占用的日志范围不会被新批次重复认领。每次任务仍受批次数上限约束。

日志归档属于操作日志转存，不是整库备份。实际环境故障恢复还需核对批次错误、源日志和对象存储内容；本地故障测试不代表线上批次已恢复。

各库使用 MySQL `server_uuid` 与库名标识，界面显示实例标识前缀。同名但来自不同实例的库分别盘点。旧快照未记录实例身份时不猜测归属，单库趋势可能从新版采样开始；总量历史仍保留。

## 统计缓存与零变化

平台库和工作空间库的盘点均在单个专用 MySQL 连接中执行 `SET SESSION information_schema_stats_expiry = 0`、读取实例身份与容量。完成或失败后销毁该连接，避免会话设置泄漏给业务连接池。设置失败按采集失败处理，不静默使用旧缓存；不修改全局参数，也不在日常盘点执行全库 ANALYZE TABLE。

该设置绕过 INFORMATION_SCHEMA 的统计缓存，但 DATA_LENGTH + INDEX_LENGTH 仍是存储引擎提供的分配空间估算，不是实际写入字节量或磁盘文件精确大小。业务写入复用已分配空间时，净变化可以为 0。页面将 0 展示为“无变化”，缺失或不兼容的对比展示为“无法比较”，明细与悬浮提示提供两次实际采样时间。

采集口径版本升为 4，升级后会补采；跨版本的首个日差不计算，避免将缓存刷新形成的差异误报成当天增长。旧历史保留原始证据，不回写猜测的容量。要判断此前某个 0 是否来自缓存，仍需在对应运行环境对照原始历史与当前查询，不能只依据截图定性。
